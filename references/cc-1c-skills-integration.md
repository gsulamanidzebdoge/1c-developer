# cc-1c-skills — გარე ინსტრუმენტარიუმი 1C-ის XML-წყაროებზე

ამ ფაილს კითხულობ მაშინ, როცა ამოცანა ეხება **1C-ის რეალურ არტეფაქტებს ფაილურ სისტემაში** — კონფიგურაციის ან გაფართოების XML-გამოტვირთვას, გარე დამუშავებას/ანგარიშს, ფორმას, СКД-ს, მაკეტს, როლს, ინფობაზას — და არა მხოლოდ BSL-ის ტექსტს.

**მთავარი წესი:** თუ [cc-1c-skills](https://github.com/Nikolay-Shirokov/cc-1c-skills) დაინსტალირებულია, **ყოველთვის მისი სქილებით იმუშავე** — არ დაწერო 1C-ის XML ხელით და არ ააწყო `1cv8.exe`-ის ბრძანება თვითონ, სანამ შესაბამისი სქილი არსებობს. ხელით დაწერილი XML თითქმის ყოველთვის ტეხს UUID-ებს, namespace-ებს, `ChildObjects`-ის რიგს ან `Configuration.xml`-ში რეგისტრაციას — და პლატფორმა ამას ხმაურის გარეშე „ყლაპავს".

| ვარიანტი | პლაგინის სახელი | სკრიპტები | მოთხოვნები |

## 2. როგორ გაიგებ, ხელმისაწვდომია თუ არა

1. **შენს ხელმისაწვდომ სქილთა სიაში** მოძებნე `epf-init`, `meta-compile`, `db-load-xml` და მსგავსები. სახელი შეიძლება იყოს პრეფიქსიანი (`1c-skills:meta-compile`, `1c-skills-py:meta-compile`) ან სლეშ-ბრძანება (`/meta-compile`).
2. თუ ვერ ნახე — პლაგინი არ არის. გადადი **§10 fallback**-ზე და მომხმარებელს ერთი წინადადებით შესთავაზე დაყენება.

არასოდეს თქვა „დაინსტალირებულია", სანამ სიაში არ დაინახავ.

## 4. ოქროს წესები

1. **არ დაწერო 1C-ის XML ხელით**, თუ სქილი არსებობს. არ მოძებნო XML-ის ნიმუშები სხვა გამოტვირთვებში — სქილების reference-ფაილები სრული დოკუმენტაციაა.
2. **ყოველი `*-compile` / `*-edit` / `*-borrow`-ის შემდეგ გაუშვი შესაბამისი `*-validate`.** ეს არის შენი „კომპილაცია"; მის გარეშე შეცდომა მხოლოდ ბაზაში ჩატვირთვისას გამოჩნდება.
3. **`*-info` კითხვისთვის, არა `Read` XML-ზე.** `meta-info`, `form-info`, `skd-info`, `role-info`, `mxl-info`, `cf-info`, `subsystem-info`, `xdto-info` კომპაქტურ ამონაწერს გვაძლევს — XML-ის პირდაპირ კითხვა კონტექსტს ფუჭად ხარჯავს.
4. **წამშლელი სქილები (`meta-remove`, `form-remove`, `template-remove`) მხოლოდ მომხმარებლის ცალსახა დავალებით.** არასდროს ავტომატურად.
5. **პარამეტრები ორივე რანტაიმში იდენტურია** — იცვლება მხოლოდ ინტერპრეტატორი:
   `powershell.exe -NoProfile -File "${CLAUDE_SKILL_DIR}/scripts/<name>.ps1" …` ↔ `python "${CLAUDE_SKILL_DIR}/scripts/<name>.py" …`
6. **პროზა მაინც ქართულად.** cc-1c-skills რუსულადაა დოკუმენტირებული — ეს არ ცვლის ამ სქილის ენობრივ წესს: გეგმა, ახსნა და ტესტირება მომხმარებელს ქართულად მიდის.

## 5. `.v8-project.json` — პროექტის რეესტრი

ერთი კონფიგ-ფაილი პროექტის ძირში (`.git/`-ის გვერდით), რომელსაც **ყველა** `db-*`, `epf-build/dump`, `erf-build/dump` სქილი იყენებს. შეიცავს პაროლებს → `.gitignore`-შია.

```jsonc
{

  "v8args": ["/UseHwLicenses+"],                           // დამატებითი არგუმენტები ყველა გაშვებისთვის
  "databases": [
    {
      "id": "dev", "name": "Разработка", "type": "file",
      "path": "C:\\Bases\\MyApp_Dev",
      "user": "Admin", "password": "",
      "aliases": ["dev", "разработка"],
      "branches": ["dev", "feature/*"],                    // Git-ის ბრენჩთან მიბმა
      "configSrc": "src\\cf",                              // კონფიგურაციის XML-გამოტვირთვის კატალოგი
      "webUrl": "http://localhost:8081/dev",               // web-test-ისთვის
      "repository": { "path": "\\\\srv01\\repo\\MyApp", "user": "Ivanov", "password": "" },
      "extensions": [ { "name": "МоёРасширение", "src": "src\\cfe\\МоёРасширение" } ]

    { "id": "test", "name": "Тестовая", "type": "server", "server": "srv01", "ref": "MyApp_Test" }
  ],
  "default": "dev"

```

დამატებითი ძირეული გასაღებები, რომლებიც ხშირად გვჭირდება: `editingAllowedCheck` (`deny`/`warn`/`off` — support-guard-ის რეაქცია), `newObjectPosition` (`end`/`byName`), `extensionApplyCheck`, `externalCheck`, `webPath` (Apache), `ffmpegPath`, `tts`.

### ბაზის ამორჩევის ალგორითმი (ერთიანი ყველა სქილისთვის)

1. მომხმარებელმა პირდაპირ მიუთითა **მიერთების პარამეტრები** → გამოიყენე ისინი.
2. მიუთითა **ბაზა სახელით** → ეძებ რიგით: `id` → `aliases` → `name` (არაზუსტი დამთხვევა).
3. არ მიუთითა → შეადარე **მიმდინარე Git-ბრენჩი** `databases[].branches`-ს (ზუსტად ან glob-ით).
4. არ დაემთხვა → `default`.
5. ვერ იპოვე ან ორაზროვანია → **ჰკითხე მომხმარებელს** ქართულად.
6. `.v8-project.json` არ არსებობს → ჰკითხე პარამეტრები და შესთავაზე `/db-list add`.

### ხრანილიშე (хранилище конфигурации)

თუ ბაზა ხრანილიშეზეა მიერთებული, ეს **მთელ ციკლს ცვლის**:

- სრული XML-ჩატვირთვა **შეუძლებელია** — მუშაობს მხოლოდ `-Mode Partial`;
- ნაწილობრივი ჩატვირთვა მხოლოდ **ჩაჭერილ (захваченным)** ობიექტებზე გადის;
- **ახალი ობიექტი მოითხოვს კონფიგურაციის ძირის ჩაჭერას**;
- კონფიგურატორის **ნებისმიერ** ოპერაციას სჭირდება ხრანილიშის რეკვიზიტები — ისინი `repository`-დან მოდის, ყოველ გამოძახებაში გადაცემა არ სჭირდება;
- გაფართოებას **თავისი** ხრანილიშე აქვს — `extensions[].repository`.

ციკლი: `db-repo update` → `db-repo lock` → `db-dump-xml -Mode Partial` → ჩასწორებები → `db-load-xml -Mode Partial -UpdateDB` → `db-repo commit`.
**ჩაჭერის შემდეგ გამოტვირთვა სავალდებულოა** — ჩაჭერა ჩუმად ამოიღებს ხრანილიშიდან სხვისი ცვლილებების ახალ ვერსიებს, და ძველი წყაროების ჩატვირთვა მათ უშეცდომოდ დააბრუნებს უკან.

## 7. ტიპური ჯაჭვები

გაითვალისწინე: ეს ჯაჭვები **ნაბიჯი 2-ის (კოდი/აგება) შიგნითაა**. ნაბიჯი 1 (ქართული არქიტექტურული გეგმა) და ნაბიჯი 3 (ტესტირება) უცვლელი რჩება.

**ახალი ობიექტი კონფიგურაციაში**
`cf-info` (ვერსია, თავსებადობა) → JSON DSL → `meta-compile` → `meta-validate` → `meta-info` (ვიზუალური შემოწმება) → **შენ წერ `.bsl`-ს** → `db-load-xml -Mode Partial` → `db-update`

**არსებული ობიექტის დამატება/შეცვლა**
`meta-info` → `meta-edit` (ატომური ოპერაციები: `add-attribute`, `add-ts`, `add-dimension`, `set-registerRecords`…) → `meta-validate`

**გარე დამუშავება**
`epf-init` → `form-add` → `form-compile` / `form-edit` → `template-add` → **შენ წერ მოდულებს** → `epf-validate` → `epf-build`
БСП-ისთვის დამატებით: `epf-bsp-init` (`СведенияОВнешнейОбработке`) → `epf-bsp-add-command`

**გარე ანგარიში СКД-ით**
`erf-init --WithSKD` → `skd-compile` (JSON DSL) → `skd-validate` → `erf-validate` → `erf-build`

**გაფართოება ტიპურ კონფიგურაციაზე**
`cf-info -Mode brief` → `cfe-init -Purpose Patch|Customization|AddOn` → `cfe-borrow` (საჭიროებისას `-BorrowMainAttribute`) → `meta-edit` / `form-edit` (საკუთარი რეკვიზიტები) → `cfe-patch-method` → `cfe-validate` → `cfe-diff -Mode A`
**თანმიმდევრობა აქ მნიშვნელოვანია:** ყველა `cfe-borrow` ერთად, პირველად — შემდგომი გადაღება `form-edit`-ის შედეგს შლის (იხ. §8).

**ბეჭდვითი ფორმა**
`img-grid` (თუ სკრინშოტია) → `mxl-compile` JSON-იდან → `mxl-validate` → `mxl-info` (არეები და პარამეტრები) → **შენ წერ `Печать()`-ს**

**როლი / უფლებები**
`role-info` (აუდიტი) → `role-compile` ან `role-edit` → `role-validate`

**ბაზის ციკლი**
`db-list add` → `db-create` → `db-load-xml`/`db-load-cf` → `db-update` → `db-run`; ცვლილებების შემდეგ — `db-load-git` → `db-update`

**ტესტირება**
`web-publish` → `web-test` (Playwright-ით ნავიგაცია, ფორმების შევსება, ანგარიშების წაკითხვა) → `web-stop`

## 8. ხაფანგები, რომლებიც ჩუმად გტეხავენ

- **`epf-dump` / `erf-dump` სავალდებულოდ მოითხოვს ბაზას შესაბამისი კონფიგურაციით.** ცარიელ ბაზაში ტიპები უკან დაუბრუნებლად იკარგება: `1cv8` აქცევს `CatalogRef.Валюты`-ს `xs:string`-ად, `ibcmd` კი „ჩამოკიდებულ" `TypeId`-ად. **შეცდომას არც დაშლა და არც შემდგომი აწყობა არ იძლევა** — „ჯერ ცარიელში დავშლი, მერე გავასწორებ" არ მუშაობს.
- **`epf-build` / `erf-build` ბაზის გარეშე ქმნის დროებით ბაზას ტიპების დანამატებით.** მუშაობს, მაგრამ რეალური ბაზა ჯობია. თუ ფორმაზე რეგისტრის ჩანაწერების ნაკრებია გამოტანილი — რეალური ბაზა **სავალდებულოა**, თორემ 1C ჩუმად ჩამოყრის სვეტების `DataPath`-ს.
- **support-guard.** მუტატორი სქილები ამოწმებენ მხარდაჭერის მდგომარეობას და **ბლოკავენ** „ჩაკეტილი" ობიექტის რედაქტირებას. ეს დამცავია, არა ხარვეზი. გახსნა — `support-edit`, ცალსახა არჩევანით: `editable` (ვენდორის განახლებები გრძელდება, შერწყმის კონფლიქტებით) ან `off-support` (განახლებები აღარ მოდის). **ეს გადაწყვეტილება მომხმარებელს ეკუთვნის** — ქართულად აუხსენი განსხვავება და ჰკითხე.
- **`cfe-borrow` თანმიმდევრობით ბოლო არ დარჩება.** `form-edit`-ის შემდეგ `cfe-borrow`-ის ხელახლა გაშვება თავიდან აგენერირებს `Form.xml`-ს და **ჩუმად ცილავს დამატებულ ველს** — `Module.bsl` რჩება, ფორმის განწკვეთილება არა. სკრიპტს, რომელსაც მომხმარებელს აძლევ, ისე აწყვი — ყველა ნასესხება ერთად, პირველად — და გადაამოწმე ორჯერ გაშვებით.
- **`cfe-validate -ConfigPath` ადგენილი შეცდომა გაფართოების ახალ რეკვიზიტზე.** მისი შემოწმება ფორმის `DataPath`-ებს მხოლოდ ბაზისურ კონფიგურაციაში ეძებს და თვით გაფართოების რეკვიზიტებს არ იცნობს. სანამ გაასწორებ — შეამოწმე, რეალურად არის თუ არა რეკვიზიტი გაფართოებაში.
- **`FormatVersion`** არ უნდა აღემატებოდეს იმ პლატფორმის ფორმატს, რომელზეც ობიექტს ხსნიან: 8.3.24 → `2.17`, 8.3.25 → `2.18`, 8.3.26 → `2.19`, 8.3.27 → `2.20`, 8.5 → `2.21`. ქვემოთ აღება უსაფრთხოა.
- **`ConfigDumpInfo.xml`-ს ხელი არ ახლო** — ეს პლატფორმის სამსახურებრივი ფაილია ინკრემენტული გამოტვირთვისთვის.
- **`ibcmd` მხოლოდ ფაილურ ბაზებთან.** გადართვა ხდება `v8path`-ში პირდაპირ `ibcmd.exe`-ის მითითებით. კონფიგურაციის გამოტვირთვისას `1cv8`-სა და `ibcmd`-ის შედეგი ბაიტობრივად ემთხვევა; **გარე დამუშავებების დაშლაზე ეს არ ვრცელდება**.
- **პაროლები.** `.v8-project.json` საიდუმლოებებს შეიცავს. არ დაბეჭდო პაროლი პასუხში და არ ჩასვა Git-ში.

## 10. Fallback — როცა cc-1c-skills არ არის

დაუბრუნდი [`source-conversion.md`](source-conversion.md)-ს და `scripts/`-ის შაბლონებს:

- დაადგინე სამი ფაქტი — ფაილის ტიპი, პლატფორმის ვერსია და გზა, ოპერაციული სისტემა;
- ააგე **მზა, გასაშვები** `.bat`/`.cmd` ან `.sh` სწორი გასაღებებით (`/DisableStartupMessages`, `/Out <log> -NoTruncate`, exit-code-ის შემოწმება, `-Format Hierarchical`);
- ქართულად აუხსენი გადამოწმება: exit-code, ლოგი, კატალოგის სტრუქტურა, round-trip (dump → load → dump → diff).

XML-ის ხელით აგება მაშინაც უკიდურესი საშუალებაა. თუ ამოცანა მეტამონაცემების ან ფორმის აგებაა და პლაგინი არ არის, უმჯობესია მომხმარებელს შესთავაზო cc-1c-skills-ის დაყენება (ერთი სტრიქონი, §1) — ვიდრე ხელით დაწერილი XML, რომელიც პლატფორმამ შეიძლება ჩუმად უარყოს.
